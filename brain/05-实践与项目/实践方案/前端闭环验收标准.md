# 前端闭环验收标准

## 核心定义

前端闭环不是“页面能截图”，而是：用户从入口触发操作后，系统能给出正确反馈、状态转移、错误恢复和最终可理解结果。

## 十类必验闭环

1. Entry：入口存在且语义正确。
2. Action：按钮/表单/手势可触发。
3. Feedback：loading/toast/error/success 可见且不重复。
4. State：URL/store/server/mock 状态一致。
5. Recovery：错误后可重试、修改、返回。
6. Finish：完成页/详情页/列表回写可达。
7. Boundary：空态、弱网、重复点击、返回中断、刷新恢复。
8. Dynamic：弹窗队列、toast 队列、StrictMode 重入、自动跳转。
9. Presentation：i18n、dark、移动端宽度、键盘遮挡、滚动容器。
10. Observability：console/network 无异常，必要埋点/错误捕获存在。

## Dead UI 判定

以下任一成立即为 dead UI：

- 可点击但无业务效果。
- 跳到不存在/只读/错误语义页面。
- 成功后没有 finish/详情/列表回写。
- 错误后无法恢复或一直停留在错误态。
- 入口被保留但功能被删。
- mock/service/API 不闭环，导致真实路径不可用。

## 红线

不能用删除按钮、删除路由、隐藏字段、静默吞错来“解决” dead UI。只有在 evidence 证明该入口不属于当前业务范围时，才能移除，并写入 ADR/decision。

## 标准执行顺序

1. 读取 Project Workpad：north star、anchors、red lines。
2. 枚举业务 flow：entry → action → feedback → state → finish。
3. 为每个 flow 写 happy path + error path + boundary path。
4. 运行 deterministic gates：lint、tsc、unit、build。
5. 运行 browser-harness/Playwright 真交互。
6. 检查 console/network/storage/service worker。
7. 截图或保存 trace，写入 Evidence Ledger。
8. 更新项目 UI_TEST_CASES/ADR/workpad。
9. 如存在高风险漂移，跑多模型 T2/T3。

## A+ 标准

- 所有 P0/P1 业务流 happy/error/boundary 均有证据。
- 无高严重 dead UI。
- 无通过删除功能制造的“通过”。
- i18n/dark/mobile 关键页面通过。
- mock/server/真实 API 对齐路径清楚。
- 当前缺口可解释、有 owner、有下一轮检查。
