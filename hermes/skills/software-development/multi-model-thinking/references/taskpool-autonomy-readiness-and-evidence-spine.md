# Taskpool autonomy readiness + evidence-spine pattern

Use this when the user asks to check local brain taskpool progress, certify long-running unattended operation, or make a PUA-loop/taskpool architecture self-run for a long time.

## Core lesson

Do not certify long-running taskpool autonomy from deterministic tests alone, and do not send a raw status file to multi-model ratification. Build an explicit evidence spine, then a claim-linked evidence state, then pass through a fail-closed ratification gate.

A first T3 run can return all planners and still fail certification with `evidence_coverage=0.0` / `needs_link_review` if evidence objects do not explicitly support the exact claim IDs (`C-001`, `C-002`, ...). Fix the state/evidence shape and rerun; never explain it away in prose.

## Evidence-spine requirements

The spine should expose stable, machine-readable evidence IDs and heartbeat-style health, including:

- task counts: active, pending, claimed, review, done, archived, stale_claims, dispatchable
- lane split: work vs evolution, and proof that work-lane preemption is not starved
- gate status: py_compile, unit tests, selfcheck, proof-check, boundary-check, diff-check
- runtime flags: autorun env, multimodel autorun env, allowlists, write guards, kill-switches
- scheduler/cron semantic health and last/next run information where available
- multimodel convergence stats: total_active, passed, triggered, pass_rate, trigger_rate
- readiness artifact: `architecture_complete`, `full_runtime_activation_ready`, `activation_blockers`

Interpretation rule: `architecture_complete=true` plus `full_runtime_activation_ready=false` can be a healthy safe default if blockers are explicit activation gates such as `autorun_env_disabled` and `multimodel_autorun_env_disabled`. Do not call this an architecture blocker unless the user expected runtime activation now.

## Claim-linked T3 state

Create concrete claims and link every evidence object to the exact IDs generated by `consult_models.py state --claim`.

Example claim set:

- `C-001`: architecture is complete and fail-closed for long-term unattended operation
- `C-002`: runtime activation is explicit and remains off unless env flags/allowlists/write guards/kill switches allow it
- `C-003`: PUA-loop stop condition is enforceable by local ratification gate; hollow certified shells fail closed
- `C-004`: taskpool progress and scheduler health are observable via evidence-spine heartbeat and readiness artifact
- `C-005`: no automatic done path exists; autorun bridge stops at claim+handoff and done requires review plus proof hash-chain
- `C-006`: regression suite and live brain selfchecks pass after scoped patch

Each evidence JSON must contain `supports: ["C-00x"]` (or the tool's equivalent grounding field), not just a citation list or raw status blob. If the first run reports `truth_status=unsupported`, `needs_link_review`, or `evidence_coverage=0.0`, regenerate linked evidence before rerunning T3.

## Ratification verifier hardening

A local ratification gate for PUA-loop/taskpool autonomy should reject hollow shells:

- status-only `certified` without positive truth evidence
- missing/empty `discussion_result.json`
- unresolved severity>=3 issue ledger entries
- missing exact canonical participant IDs for required T3 (`claude-opus-4-7`, `gpt-5.5`, `deepseek-v4-pro`, `mimo-v2.5-pro` unless state config says otherwise)
- missing `truth_status` / `can_certify_truth` / typed unsupported or contradicted claim arrays
- missing `criteria_satisfied` or equivalent final-design proof: next slice, acceptance evidence, rollback boundary, long-term goal alignment

Regression tests should include:

1. positive fixture that passes with real claim-linked evidence
2. hollow certified shell fixture that must fail closed
3. missing participant / duplicate participant / fake participant cases
4. unsupported claim / missing truth arrays cases

## Proof audit pitfall

Historical `hermes-autorun` audit lines do not automatically mean a task was auto-closed. Proof audit should only require proof hash for `review -> done` closeout performed by autorun, or for evidence explicitly containing `proof:sha256:`. A prior auto-claim line followed by human/manual closeout should not be misclassified as `autorun done missing proof`.

## Timeout and closeout discipline

For T3 quorum4 discussion:

```bash
python3 ~/.hermes/scripts/consult_models.py run STATE.json --tier T3 --quorum 4 --discussion --max-rounds 3 --timeout 240 --keep
```

If the outer command times out after planner fan-out or consensus, inspect the latest `~/.hermes/tick-*` directory for `plans/*.json`, `merged_plan.json`, and `discussion_result.json`. If there is no valid discussion/manifest, report `not_certified_yet`; do not commit or claim full certification just because deterministic gates pass.

If tool-call/context budget is nearly exhausted, preserve the exact state path, tick path/process id if any, passed deterministic gates, failed/missing ratification artifact, and next command. A final answer under interruption must explicitly say commit/certification is unfinished.

## Post-certification reviewer and live-data repair loop

A full T3 `certified` result plus local `ratification-gate PASS` is not the end if a fresh pre-commit reviewer subsequently finds a security/logic blocker. Treat the certification as applying to the pre-review diff only. Fix the blocker, rerun deterministic gates, and if the fix changes certification/security logic or evidence artifacts, rerun the target-bound ratification gate or a fresh T3 as risk requires before committing.

Evidence-spine/dispatch hardening lessons:

- Do not export raw cron job fields such as `last_error`, `last_delivery_error`, `deliver`, or `script` into evidence-spine or dispatch tick JSONL. Redact diagnostic tails and expose booleans like `delivery_configured` / `script_configured` instead.
- `evidence_spine.status == OK` is not enough. Dispatch tick must treat `gate_status != PASS` as an error/noteworthy health degradation, otherwise proof/selfcheck/boundary/cron failures become invisible in cron heartbeat logs.
- Autonomy readiness must explicitly check cron snapshot readability, required taskpool cron job presence, and auto-completer semantic safety (`ok` / `ok_with_task_blocker` plus `safe_for_next_tick=true`). Required cron jobs missing is an architecture blocker, not merely activation state.
- Use `strip().lower()` when normalizing certification/truth statuses; whitespace-only drift should fail closed or normalize deliberately, not create ambiguous behavior.

Canonical-vault data can regress while code tests pass. If real `selfcheck` / `proof-check` / `boundary-check` fails after a code fix, repair the real task note or migration data before claiming readiness. A common mission-envelope failure is `certified_requires_ratification_artifact`: for `certification_status: certified`, `ratification_artifact` must be a structured reference (`file:...`, `artifact:...`, `url:...`, or `proof:...`), not a bare absolute path. Patch both canonical artifact fields and `evidence_refs`, then rerun the canonical gates.

## Commit rule

For long PUA-loop certification/fusion work, make a scoped local commit after deterministic gates and evidence note are stable, but only claim full four-model certification after the ratification gate passes. If the user requires `4/4 全认证`, do not downgrade to 3/4 quorum or advisory fan-out. If a reviewer blocker is fixed after certification, do not commit until the final post-fix diff has deterministic gates green and certification scope is revalidated.
