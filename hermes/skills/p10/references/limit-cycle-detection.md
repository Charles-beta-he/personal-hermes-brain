# Limit Cycle Detection — 极限环检测

> ch07 非线性: 识别并打破"修A坏B"振荡；监控质变指标

## 极限环定义

极限环 = 系统进入周期性振荡，无法收敛到稳态。
Agent 中的映射: "修A坏B → 修B坏A → 修A坏B..." 的死循环。

## 检测规则

### 规则 1: 同问题复发计数

```
问题签名 = 错误类型 + 涉及文件 + 根因关键词

计数器:
  第 1 次出现: 计数 = 1，记录时间戳和修复方案
  第 2 次出现: 计数 = 2，扫描同类代码（冰山法则）
  第 3 次出现: 计数 = 3，触发极限环告警
```

### 规则 2: 修复-回退振荡

```
if 同一文件在 3 轮内被修改 ≥ 3 次:
  → 检测是否为"改回原点"模式
  → 计算文件内容的 Levenshtein 距离变化
  → 如呈振荡趋势（距离波动不收敛）→ 告警
```

### 规则 3: 验证结果振荡

```
if 验证结果在 4 轮内呈 pass-fail-pass-fail 模式:
  → 检测测试/构建的稳定性
  → 如不稳定因素来自环境 → 标记为 flake
  → 如不稳定因素来自代码 → 告警
```

## 告警与响应

| 阶段 | 行动 |
|------|------|
| 第 1 次 | 正常修复，记录问题签名 |
| 第 2 次 | 修复 + 扫描同类代码 + 标记观察 |
| 第 3 次 | **触发极限环告警** |

### 告警触发后的响应协议

1. **输出告警**: "检测到极限环: 同问题 {签名} 已复发 3 次"
2. **分析根因**: 
   - 修复方案是否治标不治本？
   - 问题是否来自更高层级（架构/设计）？
   - 是否涉及多个模块的耦合？
3. **切换策略维度**（对抗性 OODA）:
   - 从「局部修复」→「全局重构」
   - 从「自动化」→「人工确认每一步」
   - 从「增量修改」→「回滚到稳定基线重新开始」
4. **升级处理**:
   - 如 3 次切换策略后仍无法解决 → 触发 `<loop-pause>` 请求用户介入

## 数据存储

极限环检测记录:
```json
{
  "limit_cycles": [
    {
      "signature": "build-failure:src/app.tsx:type-error",
      "count": 3,
      "first_seen": "2026-04-23T10:00:00Z",
      "last_seen": "2026-04-23T11:30:00Z",
      "fixes": ["fix1-hash", "fix2-hash", "fix3-hash"],
      "status": "active|resolved|escalated"
    }
  ]
}
```
